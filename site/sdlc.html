Feature workflow

Example: let hosts confirm an early checkout while applying the existing payment, room and loyalty rules.

  1. Plan the work

    1. 1. Request a feature

      Open a Feature issue in the owning repository and add it to the Aroha Retreat Project.

    2. 2. Validate and schedule

      Agree on the user outcome, acceptance criteria, dependencies and cost. Assign a milestone and plan the story in a sprint when ready.

    3. 3. Implement

      Branch from preprod for website changes. Update shared rules, interfaces and tests. Use synthetic booking data.

  2. Review and test in pre-production

    1. 4. Open and review the PR

      Link the issue. Review the code, test evidence and rollout impact. Put the intended version and changelog in the release diff when packaging a new version.

    2. 5. Pass CI on the current revision

      GitHub Actions builds and tests the change. Resolve review comments and rerun required checks after any fix.

    3. 6. Merge and verify pre-prod

      Merge to preprod. Release any required backend first, then Hosting. Check the live revision and run the feature acceptance flow.

  3. Release and verify production

    1. 7. Open a release PR into main

      Bring approved commits onto a branch from current main. Review the release version, changelog and any backend prerequisites. Merge after checks and authorization.

    2. 8. Pass deploy gates and publish

      Check CI on the merged revision, target, artifact and compatible API. GitHub Actions uses a short-lived identity to deploy the matching Firebase Hosting site.

    3. 9. Verify and announce

      Check live version, files, protected routes and the critical user journey. Review delivery telemetry. Pages adds the release after verification, then the issue records the evidence.

Bug workflow

Example: a website integration run passed in GitHub, but its report was missing in Dynatrace.

  1. Triage and contain

    1. 1. Capture the failure

      Open a Bug issue with reproduction steps, affected versions, impact and safe evidence.

    2. 2. Choose urgency

      For active production impact, assess mitigation or a compatible rollback and verify recovery. Schedule a lower-impact fix in the Project.

    3. 3. Locate the fault

      Compare the original test run, observer receipt and tenant records. The observer’s archive reader was rejecting two expected suite files.

  2. Fix and prove the regression

    1. 4. Add a regression test

      Make the missing suites reproducible in a test. Update the reader and preserve its file, size and privacy controls.

    2. 5. Review the linked PR

      Run the affected tests and the required GitHub checks. Retest a failing case before merge. Use an app version bump and changelog for a shipped app fix.

    3. 6. Merge at the affected layer

      App fixes go through pre-prod and a main release PR. The observer fix goes to the trusted default branch because it is CI tooling.

  3. Recover and verify

    1. 7. Apply the recovery

      Deploy an app fix through its Hosting or backend release gates. For the observer, replay the original CI run and attempt using the retained report.

    2. 8. Verify the outcome

      For an app release, check the live revision and repeat the failing action. For reporting, match the receipt and find the expected suites in Dynatrace.

    3. 9. Close with evidence

      Record fix, run and live-check links. Public notes follow verified releases. Reopen if the failure returns.

CI and deployment gates

The website PR and its merged revision are checked separately. A release version and changelog are reviewed source. The pipeline publishes the chosen version and Pages reads the verified release.

Application
Tests the website and builds the frontend artifact.

Validates repository contracts, documentation links and foundation tests.
Branch policy
Enforces the promotion route. Approved changes move from pre-prod through a release PR into main.

Before Firebase Hosting

  • Match the latest branch commit to passing push checks, then recheck it after building.
  • Validate the versioned artifact, environment, site and pinned Natura assets. Check the Hosting size budget and Storage media metadata.
  • Confirm the backend version and environment are compatible. Use branch-bound identity to publish to the allowed site.

After Firebase Hosting

  • Check the provider release ID, live version and commit. Compare selected HTML, scripts, styles and media with the expected build.
  • Verify protected-route denial and the other environment’s release. Run the authorized acceptance checks in the target environment.
  • Keep the deployment and live-check receipts. Verify the Dynatrace events and deployment marker separately.

Firebase and booking emails

A browser or MCP client asks the same booking API to apply Aroha’s rules. Resend handles email delivery after a booking change has committed.

How a booking reaches the backend

  1. Firebase HostingServes the website and Studio, and routes their API requests to Functions. Developer docs use their own Hosting site.
  2. Firebase AuthenticationSigns guests and staff in with Google. MCP and integrations present scoped API tokens.
  3. Cloud FunctionsChecks permissions and applies booking, inventory, payment and loyalty rules.
Cloud Firestore
Stores bookings, availability, CMS, payment and loyalty records, audit history and queued email jobs.
Cloud Storage for Firebase
Serves public media. Private files such as guest identity documents require authorized access.

What happens after a confirmation

  1. Firestore commitsThe booking transaction writes the notification job with the verified recipient.
  2. Functions dispatchesA worker sends the queued message. The scheduled retry handles eligible delivery failures.
  3. Resend acceptsThe provider accepts the send and reports delivery to the recipient’s mail server or failure through a signed webhook.
  4. Studio shows statusThe API validates the callback and stores the delivery update. Staff can check it from the portal.

Keep booking status, provider acceptance and recipient delivery separate when investigating a missing email.

How we observe delivery and runtime

Check the delivery record to confirm what shipped. Use runtime signals to see how that version behaves.

CI execution

  1. GitHub ActionsWorkflow, job and step outcomes plus runner test reports
  2. Delivery observerReads approved runs and structured reports. Keeps the original run ID, attempt, commit and test outcome.
  3. DynatraceStores delivery events and OpenTelemetry spans, outcome counts, durations and sanitized logs.

Hosting releases

  1. Firebase HostingProvider release ID, website version, commit and environment
  2. Live probesConfirm the release files and check protected-route denial
  3. Delivery receiptsRecord deployment and verification outcomes and report a Dynatrace deployment marker for confirmed releases.

Live application

  1. Browser, API and MCPCollect browser experience after consent. Measure API requests and MCP tool attempts.
  2. Instrumented signalsMeasure latency and error rates. Use trace context and request IDs to investigate individual requests.
  3. Export and inspectBrowser RUM and configured API exports reach Dynatrace. MCP sends OTLP to the operator’s configured endpoint.
Find the change
Use the issue, PR and commit to trace the decision and reviewed source.
Verify the deployment
Match the run ID and attempt to the provider release, build version and environment.
Confirm observability
Check the export receipt and find the expected suites and outcomes in Grail by original run and attempt. A late replay keeps source timestamps on its events and traces the current reporting attempt.
Confirm a business outcome
Use the committed booking or audit record. Browser RUM describes what the guest experienced.

Telemetry uses bounded operation, status and environment fields. Guest details, tokens and request bodies stay out of exports.

Signal names used in investigations
CI and deployments
Filter aroha.sdlc by workflow, attempt and commit. Look for sdlc.check.completed, sdlc.deployment.completed and sdlc.runtime.verified.
Booking API
Use aroha.api.requests and aroha.api.duration to investigate request volume, latency and errors.
MCP
Use aroha.mcp.tool.calls and aroha.mcp.tool.duration for tool activity. Follow the trace and completion log for a specific attempt.
