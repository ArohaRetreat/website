From issue to verified release

Each step leaves a record that the next person can check.

  1. Plan

    Capture the outcome and acceptance criteria in an issue. Set its milestone and sprint in the Project.

  2. Build

    Work on an issue branch. Update the code, tests and docs together and open a linked pull request.

  3. Check

    GitHub Actions builds and tests the PR. Fix failed checks and resolve review comments before merging.

  4. Merge

    Integrate the reviewed source into the target branch. GitHub records the merge commit.

  5. Release and verify

    Publish through the owning release path and check the version and revision at its destination.

When a gate fails

Use the failing check, deployment receipt or live probe to find the fault. Fix and rerun the affected gate. If a faulty build is already live, assess rollback to a known good, compatible release and verify the restored version.

What continuous integration checks

The website PR needs four passing checks for its current revision. GitHub records each job and attempt.

Application
Tests the website and builds the frontend artifact.
Website integration
Runs API, booking, authorization and telemetry checks in isolated Firebase emulators.
Foundation
Validates repository contracts, documentation links and foundation tests.
Branch policy
Enforces the promotion route. Approved changes move from pre-prod through a release PR into main.

MCP CI checks the adapter, runs protocol and telemetry tests and previews the npm package. Developer docs CI builds the static site and tests its generated references and Swagger setup.

Where releases go

The website’s delivery workflow checks the branch head and CI before deploying with a short-lived identity. Backend changes have their own reviewed release step.

Website and Studio

  1. Checked branchpreprod for testing or main for production
  2. Firebase HostingBuild and deploy to the site assigned to that branch
  3. Verify liveMatch the Hosting receipt, source revision and live files

Booking API

  1. Reviewed API changeValidate contracts and rules in isolated tests
  2. Firebase FunctionsRelease the affected backend to the approved environment
  3. Verify runtimeCheck API version, environment and protected routes

MCP package

  1. Reviewed packagePass CLI, contract and packaging checks
  2. npm publicationPublish the tested package version
  3. Verify availabilityCheck registry metadata and smoke-test the published CLI

Developer docs

  1. Reviewed docsBuild the reference and test its API provenance
  2. Dedicated HostingPublish to the developer documentation site
  3. Verify liveCompare the release manifest on both public domains with the source commit

How we observe delivery and runtime

Check the delivery record to confirm what shipped. Use runtime signals to see how that version behaves.

CI execution

  1. GitHub ActionsWorkflow, job and step outcomes plus runner test reports
  2. Delivery observerReads the website’s allowed runs and uses the source run ID, attempt and commit
  3. DynatraceDelivery events and OpenTelemetry traces, metrics and logs

Hosting releases

  1. Firebase HostingProvider release ID, website version, commit and environment
  2. Live probesConfirm the release files and check protected-route denial
  3. Delivery receiptsRecord deployment and verification outcomes and report a Dynatrace deployment marker for confirmed releases.

Live application

  1. Browser, API and MCPCollect browser experience after consent. Measure API requests and MCP tool attempts.
  2. Instrumented signalsMeasure latency and error rates. Use trace context and request IDs to investigate individual requests.
  3. Export and inspectBrowser RUM and configured API exports reach Dynatrace. MCP sends OTLP to the operator’s configured endpoint.
Find the change
Use the issue, PR and commit to trace the decision and reviewed source.
Verify the deployment
Match the run ID and attempt to the provider release, build version and environment.
Confirm observability
Check export acceptance and search for the expected event or signal in the tenant. Trace joins require real trace context.
Confirm a business outcome
Use the committed booking or audit record. Browser RUM describes what the guest experienced.

Telemetry uses bounded operation, status and environment fields. Guest details, tokens and request bodies stay out of exports.

Signal names used in investigations
CI and deployments
Filter aroha.sdlc by workflow, attempt and commit. Look for sdlc.check.completed, sdlc.deployment.completed and sdlc.runtime.verified.
Booking API
Use aroha.api.requests and aroha.api.duration to investigate request volume, latency and errors.
MCP
Use aroha.mcp.tool.calls and aroha.mcp.tool.duration for tool activity. Follow the trace and completion log for a specific attempt.
