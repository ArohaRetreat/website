# Production and pre-production delivery

Issue72; website0.21.3, API0.7.1. One repository, two long-lived branches: `main` is production and `preprod` is pre-production. This replaces the earlier recommendation against permanent environment branches. Environment selection is configuration, never a fork of booking policy or content. Host CMS, reservations, identities and original assets are not branch state.

Work through short-lived issue branches and PRs. Both environment branches require current checks (`application`, `website-integration`, `foundation`, `branch-policy`), resolved conversations and linear history. Direct pushes, force pushes and deletion are blocked, including administrators. Required review count is zero for this single-maintainer repository; passing checks and a PR are still mandatory. The trusted `pull_request_target` policy executes inline code only, with no checkout, secrets or write permissions, and rejects direct PRs between main and preprod in either direction. Do not bypass that check. For promotion, create an independent release branch from current main, cherry-pick only approved commits, resolve and review the diff, then submit a normal main PR. A common initial revision does not imply future branches are automatically merged. Administrators can change repository policy deliberately; these controls prevent routine mistakes, not a malicious administrator.

`Deploy environment frontend` runs on pushes to these two branches (with `AUTO_HOSTING_DELIVERY=true`), or explicit dispatch on one of them. It waits for all current-source checks, refuses a superseded head, builds the matching environment without emulator helpers, and rechecks before authentication. Concurrency is serialized per branch without cancelling in-progress publication. A dispatch has no target/environment/source override input. GitHub environment policies allow only main→production and preprod→pre-prod. Tags, PR refs, other repositories and other branches cannot select a target.

Two Google service accounts use separate Workload Identity Federation providers. Trust requires numeric repository/owner IDs, exact ref, exact workflow path/ref, environment subject and push/dispatch event. No service-account keys or Firebase refresh tokens are stored in Actions. A custom Hosting publisher role allows existing Hosting reads/updates and metadata reads needed for rewrites; it grants no Functions, Firestore, Storage, Secret Manager or IAM writes. Hosting IAM permissions are project-level: site separation is enforced by branch/environment/provider/workflow and guarded artifact/target checks, not a claimed site-level IAM policy. The deploy script has a fixed Hosting-only command; credentials are not granted to PR test jobs. Existing DT delivery token is used only by trusted deployment/reporting jobs.

main builds production origin/runtime and preserves the pinned Natura0.6.1 source export; preprod builds the test banner, noindex and test origin with its separate RUM metadata. Upstream ZIP packaging embeds timestamps, so two published original-art archives are retained using pinned compressed hashes, rather than replaced by rebuild variants. Every design path/hash must also match the authoritative current Hosting inventory before production publication. Source/release/environment/site/directory must all match. Public API runtime must identify the same environment and compatible API0.7.0 before frontend deployment. Exact source hashes, protected401 responses, provider release and opposite-site preservation are checked after publication. Receipts retain14days in Actions. Deployment ingestion, searchable signals, real-account browser acceptance and native RUM linkage are distinct evidence.

Automatic publication is **Hosting only**. Backend/source API upgrades, rule/index/TTL changes, secret bindings, mail activation and data migrations require their own reviewed explicit release. A frontend gate fails closed if its compatible backend has not been deployed. Production mail remains off until real host reply/notification address, billing address/payment instructions and production Resend credentials/webhook are configured and approved. Frozen email/PDF review designs are not integrated by this release.

Initial production cutover preserves existing owner/env values, deploys only API and booking-event worker from a committed clean source with mail off, verifies runtime/config/policy/indexes, then publishes Hosting through GitHub. No CMS seed or live synthetic booking is used. Production0.19/API0.6 Hosting rollback requires restoring its compatible backend source/config only if needed; retain current content, bookings, notification/invoice ledgers and all original media. Do not replay historical outboxes or roll back customer data.

Old branches are audited against PR history and preserved with `archive/branches/2026-11-05/<branch>` tags and an ignored manifest/bundle before deletion. Unmerged automated dependency updates are archived and closed without being merged. Only main/preprod remain after cleanup; new work branches are temporary and automatically deleted after merge. Archive tags are protected against update/deletion. Do not delete a new or moved branch based on an old manifest.
