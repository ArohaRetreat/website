# Booking platform contract — website0.19.0 / API0.6.0

Owner-approved issue63. Existing schema/policy/prices/CMS/records stay intact; additive API version with new contact requirement on new reservations. No emails/payments/audio.

## Exclusive range
Guest chooses inclusive first/last event dates. New requests use exclusive API departure=lastDate+1, maximum31 event days. Site reserved continuously first day configured dayStart through last day dayEnd, including intervening nights. Accommodation not included; explicit host agreement required. Existing snapshots retain old single-day epochs. Host offer, guest acceptance, atomic conflict recheck and expiring hold apply to the entire interval. Events never earn stay credits. Adult onsite35 cap applies; event capacity does not promise beds.

## Private profile/contact
GET /booking/profile returns own {name,phone,email,version}; Google email comes from verified claims, never accepted from body. POST /booking/profile {name,phone,expectedVersion} validates E164 international phone (+8..15 digits), name2..120, version; API idempotency applies. Uses existing private aroha_booking_profiles documents without replacing counters/other fields. POST /booking/guest-profile {guestId} is a booking-manager-only bounded lookup for manual reservations. Booking-contact read allows the owner and authorised booking staff. New create accepts contact:{name,phone}; if absent, uses stored valid contact, else CONTACT_REQUIRED. Booking contact snapshot persists; future profile edits do not rewrite past reservations. Host manual create supplies the registered guest's contact. Host bulk/calendar/ledgers/audit/idempotency projections must not expose contact; own profile and owner/authorised booking-contact read only. No direct Firestore access. CONTACT_REQUIRED, INVALID_CONTACT, VERSION_CONFLICT are bounded errors.

## Unified Host Studio/access
One /admin/ authenticated shell; Website changes and Bookings are capability-controlled modules, with People & access for authorised access managers. Existing /admin/bookings/ forwards into that shell. Internal module documents are implementation details, protected by the same server permissions. Mounted modules remain in memory while switching so website drafts survive. Legacy membership defaults retain existing access: active superadmin/admin both modules/manage bookings, editor website editing only, viewer website reading only. New membership fields websiteAccess:boolean and bookingAccess:none|viewer|manager are independently assigned with expectedVersion by existing authorised admins subject to protected owner/peer rules. No public/self privilege assignment. Website-disabled staff cannot read/publish/upload CMS media. Booking viewer cannot mutate, including direct API calls. Re-read access in transaction, not only hide navigation. Module-grant edits require expectedVersion and increment the member version; legacy role-only clients preserve module fields. Legacy roles still constrain CMS publishing and access management. Revocations take effect on protected requests.

## Business observability
Canonical provider aroha.booking, namespace aroha-retreat, schema2. Client form events are explicitly client-reported; server request outcomes server-observed; transaction outbox events server-confirmed. Every event has stable event ID, journey/request/transaction correlation where available, finite step/operation/outcome/kind/error enums and real capture trace/span context. No fake browser ancestry. Server response events describe operation/status/error/duration/resource state, not raw bodies. Auth failures never infer phone. Validated stored/snapshotted guest phone is owner-authorised in server-owned business event contact.phone only; not metric dimensions, URLs, general logs, trace baggage or browser payloads. Names/email/notes/addresses/child ages/promo codes/tokens never exported. Profile/booking forms disclose essential operational monitoring and phone export; existing optional RUM/GA consent is preserved. Detailed client funnel events follow monitoring consent; essential server outcomes/commit audit always captured. Network interruption means client observations can be missing; do not claim zero-loss browser tracking.

Private server-only aroha_observability_outbox holds bounded events, delivery lease, attempts/nextAttemptAt and delivered expiry. New scheduled worker drains bounded batches with retry/backoff/jitter;202 alone accepted, failures retained. No external call inside retried domain transaction. Cutover only schema2 new events; existing booking/email audit outbox stays untouched. At-least-once delivery, stable-ID consumer dedup; delivered queue TTL7days, monitoring workspace retention governs exported events. No historic replay without explicit action. Additional function/Firestore/Dynatrace ingestion usage disclosed to owner. Token remains existing Secret Manager binding, never browser. New indexed query requires READY and exact probe before deployment.

Validation covers range/exclusivity/legacy snapshots; profile ownership/version/contact inheritance/snapshot/private projections; module grants/viewer denials/revocation/storage rules/draft retention; strict event envelopes/PII boundary, request failures, committed events, retry leases/idempotency and actual tenant searchability of synthetic new events. API/worker/rules/indexes precede Hosting; protect CMS/Natura and existing bookings. Deploy/ingest/searchability/real-user/device checks separate.

API response capture has a two-second database budget and bounded direct Dynatrace fallback when the application database is unavailable. It never changes an already committed booking result. A complete database+network outage can still prevent external capture; bounded local capture-failure logs remain. The same stable event ID can arrive through both paths, so analytics must deduplicate.
