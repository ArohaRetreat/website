# Guest navigation and mail parity — website0.23.0/API0.8.1

Issue86, preprod first. Completed guest Google sign-in returns to `/`, including public website/map, enquiry gate and booking guest sign-in; host authentication retains Host Studio. Restored authenticated sessions do not loop-redirect. A dismissed sign-in dialog cannot initiate delayed navigation. Booking search stops after its sign-in redirect, without issuing a quote or reservation. Booking exposes a visible Back to website link above its header at every viewport and atmosphere; native links preserve normal navigation.

MAIL_RECIPIENT_MODE is server-owned, booking|test-inbox. Production uses booking; preprod defaults test-inbox for compatibility and explicitly switches to booking for this release. New booking-mode jobs snapshot the server-verified guest profile email for acknowledgements/confirmations and configured hostTo for host notifications. No client-supplied recipient. Reply-To is the configured host address, not a forced test inbox. Preprod tester allowlist and isolated booking/outbox/invoice namespaces remain; subject/body/PDF test identity and telemetry environment remain explicit.

Jobs snapshot recipientMode and recipient when created. Historical preprod jobs without that field are legacy test-inbox jobs and retain the original inbox. They are not rerouted or replayed. Delivery checks environment, test identity and snapshotted recipient policy. Rolling configuration back to test-inbox must refuse booking-mode sends; it never changes their recipient. Signed webhooks still verify the stored actual recipient, environment, provider ID and replay state. No migration/replay of existing notifications or invoices and no public invoice storage.

Payment gateway is not needed for the current payable invoice/manual-payment flow. Production can use the already configured provider account, domain, sender and host inbox. Remaining owner inputs are invoice issuer address and wording for payment instructions (for example, pay directly with hosts); real configured addresses/credentials stay private. Remaining implementation/deployment: complete approved frozen graphical lifecycle templates/PDF integration, check-in welcome, host manual payment recording and checkout invoice showing actual paid/balance, one24-hour private feedback invitation/form, production runtime secret/sender bindings and webhook, activation cutover for new events only and live acceptance. Do not call an unpaid invoice a paid receipt. Existing three-email flow is not the complete lifecycle.

Required validation: guest/host recipient separation across atomic booking→approval jobs; no caller recipient override; old queued recipient preservation, configuration rollback denial, duplicate/uncertain-delivery recovery and signed recipient checks. Redirect and no-post-redirect-booking tests; desktop/phone visible navigation; actual API/Auth/Firestore/Storage emulators; current-head CI and scoped preprod backend then frontend with unchanged production baseline. Real inbox, Google and physical-device evidence are separate from emulators/provider acceptance.

Rollout order: update preprod email dispatch/retry (backward-compatible with legacy jobs) and event worker first, then the API. Frontend0.23 requires API0.8.1 minimum in both publication and live verification. Preserve the old forced inbox privately for legacy jobs; do not change their addresses.
