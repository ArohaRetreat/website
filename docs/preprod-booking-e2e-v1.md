# Pre-production booking acceptance v1 — issue101

The test console is built only for pre-prod at /admin/testing/. It uses normal Firebase Google sign-in and existing API permissions; no custom token, reserved claim, fake Google identity, shared test membership or authentication bypass is allowed. A host manager runs both guest-scoped and host-scoped calls under their real session. A second real identity is required to certify cross-account ownership. API-driven scenarios and a normal guest UI journey are reported separately.

Before writes, verify environment/source, a free future test window and existing user records. Use bounded run-owned fixtures, at most three active requests, normal published rates and no global settings/room readiness changes. Do not edit existing bookings or CMS. No payment is recorded. Use synthetic contact details only inside explicitly labelled preprod test bookings; do not overwrite the signed-in user's profile. New test email goes to the actual signed-in tester and configured host. Retire only run-owned records and promos; preserve invoice/audit history. Normal business signals come from the server; test assertions are runner-observed.

Report schema1: runId(UUID), source(SHA), environment(pre-prod), startedAt/finishedAt, execution(live-browser-api/live-api-read/emulator/live-guest-ui), cases[{id,status(passed/failed/blocked),startedAt,finishedAt,code,bound bookingIds/requestIds}], cleanup. No names, emails, phone, notes, credentials or raw API bodies in exported reports. Private evidence may retain bounded record IDs. Metrics use only finite scenario/status/execution labels, never run or booking IDs.

Dynatrace test provider aroha.testing uses service aroha-e2e-tests-pre-prod, test.is_synthetic=true, test.run.id, test.scenario.id and test.execution.kind. Authority=test-runner-observed. This is distinct from aroha.booking server-confirmed outcomes; correlate live requests using X-Aroha-Journey=runId and returned request/booking IDs. Emulator execution is explicitly labelled demo-aroha and cannot certify a live Google session or preprod commit. Use server-owned configured preprod destinations/secrets, never browser-exported tokens. Verify ingestion and tenant searchability independently.

Coverage includes day/shared/private/exclusive pricing and capacity, children/room allocation, continuous ranges, closures, active limits, duplicate/stale requests, approval/rejection/cancellation, amendments, promo limits, profiles, ownership, signed webhooks/private invoices, reduced-motion/phone layout, consent and auth denials. Temporal expiry/turnover/loyalty/retry-failure scenarios run in controlled emulators when wall-clock preprod cannot exercise them safely. Missing check-in/checkout/payment/feedback email features remain blocked requirements under issue70, not passed tests. No production reservations or production configuration writes are part of this run.


When the actual tester already has two active reservations, preserve both. Run sequential fixtures under the normal three-active limit. The mixed capacity case reports `held-and-quoted`: hold ten overnight adults, allow a quote for25day adults plus two children and deny26day adults. This verifies live capacity evaluation without falsely claiming two new committed holds. With sufficient headroom, `two-held` commits both allocations then denies another adult. Keep the variant in test events and evidence. Three existing active reservations block new fixture creation; never cancel them or raise the limit to make tests pass.

Completed runs automatically download the sanitized JSON report, so results can be retrieved without another login if the Mac locks. Keep the Safari tab open; browser/OS suspension can still delay execution. The manual download button remains available. This exports no authentication tokens or contact details.
