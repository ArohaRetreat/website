# Manual booking, verified customer identity and nightly credits — contract 1.3.0

Owner decisions: one credit = INR1; level1/2/3 earn100/200/300 credits per eligible completed night; no redemption cap other than the current amount payable. Keep existing Visitor/Friend/Family thresholds6/10 qualifying completed visits. Apply credits after the existing best eligible tier/promotion benefit; no cash-out, negative total or reward for cancellation, day visit, event, uncompleted or duplicate night. No credit expiry in v1. No historical bulk import.

Customer identity: retain existing Firebase UID as the account actor, use a stable private customer profile for a manually entered new email, and link only after verified Google sign-in proves that same normalized email. One current account binding, at most one unclaimed customer alias; conflicting linked identities need review. Manual quote and confirmation recheck any connected account’s current verified Auth email and refuse recycled or changed identity matches. Do not fabricate Auth users, transfer a linked account through contact edits, place raw email/phone in URLs/telemetry, or rewrite immutable financial owners. Every own-row history, detail, mutation, document, feedback and erasure policy resolves the current same binding. Existing scoped grants are never widened.

Admin booking: explicit name/email/phone; server-priced quote and availability under current shared rules; review then one confirm action, no second self-approval. New customer is a private operational profile, not a Google account. Confirm in one inventory/idempotency transaction and queue one real confirmation/invoice. Actual check-in, checkout, cancellation and decline queue their own operational notifications; optional private feedback remains due24h after checkout. Delivery status distinguishes queued/accepted/delivered/failed. No duplicate historical/imaginary stage email.

Credits: append-only earn/hold/redeem/release/adjust entries, integer credits/paise and current wallet version. Earn100/200/300 once per distinct eligible overnight date at the snapshotted level; multiple rooms do not multiply the account reward. Concurrent completions/readjustments cannot duplicate a night. A pending request reserves credits; only confirmation consumes them. Cancellation/decline releases a hold or restores consumed credits exactly once. Expired holds stop reducing spendable balance by server time independently of TTL/deletion and reconcile lazily/audited. Quote/Create recheck actual available balance, current price, grant/member/client and versions. Repricing/date changes may not silently alter a contracted redemption; require a new explicit credit decision or reject safely. The financial invoice snapshots the approved loyalty discount separately from any tier/promotion discount, not a cash payment.

REST additions: POST /customers/lookups (bounded private read body), GET /customers/{id}, POST /manual-booking-quotes, POST /manual-bookings, POST /me/customer-link, GET /me/loyalty, GET /me/loyalty/entries, GET /customers/{id}/loyalty, GET /customers/{id}/loyalty/entries, POST /customers/{id}/loyalty/adjustments. Explicit module/current-contact scopes for lookups and manual writes; own/all loyalty scopes and manager-only adjustment. Existing quotes accept optional redeemCredits and snapshot credit and price-benefit discounts; check-in snapshots the earning rate. Actual credited dates intersect the booked overnight interval with the actual IST check-in/checkout dates, at most31 nights. No-show retains confirmed redemptions under the existing financial terms and earns no credits. Redeemed bookings reject date changes with CREDIT_REDEMPTION_CHANGE_REQUIRES_REBOOKING; cancellation restores credits before rebooking. Mutable operations use If-Match and stable Idempotency-Key; errors include current private identity conflicts, insufficient credits, stale quote/wallet, duplicate operation and reconciliation required. MCP uses the same typed REST definitions and annotations, no direct database access. Read-only credentials keep their original ceiling.

UI: add booking as a focused three-step flow with a persistent guest/visit/price summary and one clear primary action. Customer search begins empty with bounded server lookup instead of a50-user select. Guest loyalty page shows available credits, reserved credits, rupee value, current level, next-level progress, earn rate and paginated activity. Checkout explicitly chooses how many credits to apply and shows remaining credits/payable amount. Host loyalty view is search-first and has selected customer balance/activity plus a separate reason-required adjustment dialog. Payment ledger and private feedback have their own clear navigation/empty states with permission-aware actions; booking decision panel presents the next relevant action rather than a row of competing buttons.

Required tests: verified/unverified/wrong-email claim, account binding conflict/revocation, privacy erasure, cross-user/doc/feedback ownership, duplicate/concurrent manual confirmation, capacity rejection, earning tiers/night deduplication, simultaneous redemption, expired/cancelled/refused holds/refunds, adjustment consistency, immutable invoice snapshots, operation replay/preconditions, search/cursor bindings, permission revocation,10kcustomers/100kbookings synthetic bounded-query validation (not a concurrency guarantee), browser review desktop/mobile with long names/emails/empty/errors and actual local email provider delivery. Preprod first, then reviewed production promotion; explicit real booking changes are separate receipts, never test fixtures.


## Operations and scale

Canonical [OpenAPI](external-v1.json) contains121 operations. Further additions are GET /host/reservations (exact reference and/or stored status), GET /customers/{id}/reservations (current linked owner IDs, optional stored status), GET /host/booking-summary (consistent read-only aggregate snapshot), GET /payments and GET /feedback/review (optional exact booking reference). Booking staff need reservations:read/all for host queries, payments:read/all for the ledger; private feedback review requires feedback:read/all and booking manager access. Customer contact lookup/get requires contacts:read/all and manager access; loyalty reads require loyalty:read and current own/all row policy. Adjustment requires loyalty:adjust/all plus manager access and strong loyalty ETag. Manual quotes/confirmation require both reservations:manual and contacts:read/all. Identity claim is customers:link on the verified own account.

Customer lookup returns at most10 results and a refine-search hint, using a private POST body to keep contact searches out of URLs. Lists default25/max50 and bind private15-minute cursors to account, grant/version, filter, owner binding and page size. Host state no longer downloads the latest50 customers. Stored status filtering is explicit: an elapsed pending hold is projected as expired even before cleanup changes its stored status. Summary subtracts elapsed holds from pending and adds them to expired. Native aggregate queries run in a separate read-only snapshot so the role/audit transaction does not lock every reservation. Counts are informational, never inventory authority.

Derived profile search fields are populated by scripts/backfill-customer-search.mjs --environment <pre-prod|production>, dry run first, then --apply. The script touches only searchName/searchEmail/searchPhone, skips erased profiles, uses update-time preconditions, rereads writes, records private checkpoints per page and can safely rescan already normalized records. It never creates email-key bindings, Auth users, wallets or historic credit awards. The20,000-profile run bound requires explicit review beyond that size.

A cancelled/declined/expired invoice has zero current payable balance. Historical charges and verified payments remain visible for host review; cancellation/reversal does not transfer a refund. New credit invoices use pdf-v4-loyalty and distinguish price benefits, credits and actual payments. A fully credited invoice is settled without inventing a cash payment. Frozen legacy email-v3/PDF-v4 renderers/assets remain unchanged.
