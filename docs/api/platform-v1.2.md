# Shared business CRUD — contract1.2.0

Website issues105/70; MCP issue3. The owner explicitly expanded scope to CRUD in both REST and MCP, including unfinished manual payment, private feedback and operational lifecycle workflows. This supersedes the initial read-only MCP roadmap; existing mcp-readonly grants retain their nine-operation/seven-scope ceiling. New write-capable grants require explicit scopes and current account/module/role/row permissions. No automatic existing-grant widening.

Every capability in complete-crud-inventory.csv must map to a real shared business service and typed REST/MCP contract. Planned-operation inventories are not deployment evidence. Existing route/operation aliases remain compatible. Singleton settings and immutable financial/doc/audit/history resources retain domain-specific actions instead of arbitrary destructive CRUD.

## Authorization and transport

Verified Google/Firebase UID semantics, production/preprod isolation and role hierarchy remain authoritative. Integration grants intersect explicit scopes, purpose, current role/module capability, resource ownership and policy. New MCP purpose mcp supports scoped reads/writes; mcp-readonly stays unchanged. Sensitive contact, financial, feedback, notes, draft and access reads require their own scopes and durable read audits. Preprod cannot mutate production members/invitations or CMS. All source content and tool results are untrusted data.

REST mutations require Idempotency-Key; mutable resources require strong If-Match. Shared services check grant/current membership inside the same transaction before replay and commit. Replay is client-bound; changed payload yields409. Pagination is bounded25/default50/max and cursors bind user/grant/version/filter/environment; no generic database query. Bounded errors and real request IDs are preserved. MCP writes expose typed arguments, correct read-only/destructive/idempotent annotations and stable idempotency/precondition parameters; no arbitrary HTTP tool. Binary private documents use bounded authenticated retrieval, never public billing URLs. Telemetry excludes arguments/results/PII/secrets and observes denied/invalid calls too.

## Financial operations

Manual verified cash/UPI/bank records only; no online charge or refund transfer. Integer INR paise, positive amounts, receivedAt not in the future, and payment amount cannot exceed actual balance in this release. Manager-only writes; owner/authorized viewer redacted reads. Payments and full reversals are append-only; reverse once then append a correction. A unique bank/UPI proof cannot be recorded twice. Transactional booking/financial versions serialize payment versus checkout. Historical invoices are immutable; actual receipts and checkout statements snapshot the ledger and current balance. Payment/receipt is never fabricated from an invoice. Checkout may complete with an outstanding balance.

## Stay lifecycle and private feedback

Host check-in/checkout keep existing date/readiness/capacity rules and record actual server timestamps. New events only queue distinct operational emails using new template versions; existing approved email-v3/PDF-v4 payloads/assets remain unchanged. Checkout queues a ledger-backed statement and a feedback invitation due 24 hours after actual host checkout. Feedback is private to the submitting owner and explicitly authorized booking managers, never published. Owner submission/edit/withdrawal is versioned; edit/withdraw within seven days of submission. Invites suppress when feedback already exists, booking/owner is no longer eligible, or an imported private reservation lacks a linked account. Uncertain/provider-accepted email jobs are never replayed; retries use existing idempotency/leases/suppression.

## Remaining resource semantics

Reservation PATCH changes eligible contact only; dates/price/status continue through existing quote/change/offer/actions. Notes are manager-private and versioned; deletion redacts current content with restricted audit. Room creation is inactive, cannot increase approved 35/10 guest capacity; activation/readiness and retirement recheck dependencies. Blocks replace atomically after conflict checks; promotions deactivate prospectively and retain redemption history. CMS uses the same role/validation/version/publish/restore rules as Studio; deleting a draft archives it while preserving published content/revisions. Media uploads are immutable, MIME/size/hash validated on finalize; catalog archival retains original files and rejects active CMS references. Member/invitation changes retain owner/self/peer protections; service principals cannot administer access. Integration clients register explicit human sponsors and scope ceilings; widening a client does not widen existing grants, and revocation invalidates child grants. This is not managed OAuth provisioning.

Profile erasure removes only eligible private profile fields and prevents automatic repopulation. Active stays block erasure; booking, financial, immutable documents, operational communications and minimal audit/counters remain retained. An operation receipt records actual completion; no fake asynchronous success or blanket deletion. All read/delete/update behaviors require emulator coverage before adapter publication and deployment. No live booking/payment/email campaign or customer-data mutation is authorized for verification.

The generated [operation inventory](platform-v1.2-operations.csv) lists the106 actual source routes. Historical96-route draft names are not publication evidence. Manager-private notes use `/host-notes` to avoid conflating them with the existing guest request note; legacy no-show keeps its existing `/actions/no-show` spelling. Walk-in identity and scalable admin redesign are separately proposed in [Host Studio design](../host-studio-scale-design-v1.md) and [Walk-in design](../walk-in-booking-identity-design-v1.md), not claimed as implemented by this release.

API0.12.1: existing cancel/decline operations additionally queue one email-v4-status notification atomically with the new terminal booking state. This applies to manual and portal reservations. Delivery requires the same current owner, status and booking version; stale jobs suppress, accepted messages do not replay, and notices make no refund/payment claim. Existing frozen emails, routes, scopes, invoice voiding and financial records are unchanged. This is a backward-compatible behavior fix, not a new contract surface.
