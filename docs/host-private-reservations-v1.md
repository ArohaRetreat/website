# Host-recorded exclusive reservations v1 / issue91

Server-only operations for authorised host imports. No public client write route, fabricated Google login, account provisioning or required invented phone/attendance. Caller uses configured server credentials; each transaction re-reads an active booking-manager membership. Source is host_private; confirmed event reservations reserve the whole continuous interval, independent of unknown attendance. Display Privately booked, named customer and Guest count to be arranged in Host Studio. Guest/public projection never exposes customer email.

Input: customer name/email;1–2 ranges with stable operation key, arrival and inclusive lastDay, paise dayRate; optional existing pending event id+expectedVersion for explicitly approved conversion. Strict calendar dates, future horizon365days, maximum31inclusive days/range, positive integer bounded dayRate, valid email/name. Price is inclusiveDays×dayRate, snapshotted; no paid receipt/tax claims. Guest capacity probe uses the shared exclusive availability policy, not a claimed real party count. Confirmed rows store unknown attendance explicitly. New ranges cannot overlap one another or existing active/pending reservations, maintenance or overdue presence. Pending expiry uses server time. Transactions read bounded active records and config/ledger/profile/request/membership before any write; config guard and daily ledgers serialize with normal guest bookings. Conflicts, stale versions and replay with changed input fail closed; identical retries return the original records. No automatic cancellation or old-owner reassignment without explicit id/version input. Conversion retains the original reservation snapshot in private audit and removes only its linked expiring offer hold, updating both owners' active lists. No legacy mail replay.

Notification is a separate idempotent host operation after real billing/sender configuration is ready. It snapshots an unpaid private invoice and one approved branded confirmation, atomically with its durable notification job. Explicit host customer email is distinguished from Google-verified guest mail. The offline customer's CTA explores the website and invites a reply; it does not promise access to an unlinked guest account. All original email-v3 payloads remain unchanged; private confirmation uses email-v3-private. Accepted invoices/jobs cannot be silently regenerated or replayed. Deliveries use production workers/key and a separately signed production webhook, with environment/recipient checks.

Anonymous calendar may add only reason=already_booked for unavailable ranges overlapping confirmed private-exclusive inventory; no name/reference/email/count/rate is public. Room/event Host Studio calendars show the real reservation and open the existing access-controlled detail. Cancellation releases this booking's ledger capacity normally; no independent permanent block remains.

Audit/business events use bounded operation, booking/job/invoice IDs, authoritative host actor and environment, never customer name/email/notes/bodies. Normal runtime OTel and deployment evidence retain existing semantics. No collection-index migration or CMS seed write. Production activation uses new-event-only cutover; preprod data/queue/RUM stay separate. Production secret/webhook/billing setup is a prerequisite for sending, not for recording the authorised inventory reservation. Explicit source/config/target checks precede publication, with preprod/CMS/Natura preservation. Remaining lifecycle/PDF renderer integration remains issue70.

Operator: scripts/record-private-reservations.mjs --production --input PRIVATE_JSON --key STABLE_KEY defaults to read-only dry-run. --apply additionally requires a private receipt path, clean current origin/main source, exact matching published production release and authenticated project credentials and one active configured authorising host; it records the actual operator principal hash and rechecks host membership. --notify uses only id/expectedVersion and validated live mail configuration, one immutable confirmation per booking. Never commit customer input or credential files. Billing may include an optional establishment registration number, explicitly labelled separately from GST/tax identifiers.

Operator imports are not browser sign-ins. The CLI authenticates using the existing project credential, derives a non-PII operator principal hash from that credential, and independently resolves/rechecks the configured active authorising host. Audit actor/recordedBy is the real operator identifier, with authorisingHost recorded separately; no Firebase user or application membership is created or impersonated. SDK credentials are held in an owned temporary ADC projection and removed after the operation. No operator identity can be supplied through customer JSON.
