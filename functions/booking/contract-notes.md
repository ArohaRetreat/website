# Production booking API v1 — 0.4.0

All routes are /api/v1/booking/*. Public GET /public exposes only settings and room inventory. Other routes require a server-verified, non-revoked Firebase Google identity with verified email. Host workspace requires an active admin/superadmin membership, re-read inside each mutation. Guest identities never enter the host-membership admission route automatically.

GET /state?admin=1&start=YYYY-MM-DD&cursor=OPAQUE returns a projected, bounded snapshot; guest pages are own-only (25/page plus at most3 independently projected active reservations); host pages combine25 recent reservations and14 calendar days. Cursors are private server records bound to actor/view and15-minute expiry. No private booking data is cacheable.

POST routes: availability, quote, create, booking-action, note, change-quote, change-request, settings, unit, promo, block, unblock. Bodies follow contract.json; all writes require Idempotency-Key. All guest owner IDs, roles, totals, tiers and booking status are server-derived. Host-created requests can target registered guest IDs only. Structured error response remains {error:{code,requestId}}.

Inventory is whole-unit, half-open local IST dates, maximum31 nights and365-day arrival horizon. Capacity10; two tree houses/two cottages at2 each active. Fifth and four future rooms inactive. Owner confirmed no existing commitments and authorised launch with host-agreed pricing. No online prices/payment at launch: rates null, discount0 and totals null, clearly labelled. New requests require host approval and expire after24hours; no financial cancellation charges and guests can cancel before arrival. Settings may be tightened prospectively, snapshotted per booking.

Firestore transactions read current configuration/guard, membership, actor/owner profiles, idempotency/quote/target reservation and every affected nightly ledger before writes. Nightly ledgers atomically enforce whole-unit and overall occupancy. Configuration guard serialises closures and reservation mutations. Expired pending leases do not consume capacity regardless of cleanup timing. Date changes keep original allocation until host approval, then replace it atomically. Per-account active request limit3; durable per-minute API quotas. Idempotent exact replay cannot duplicate reservations or credits. Profile completion credit changes only on a valid transition to completed.

Private collections: aroha_booking_config, aroha_booking_days, aroha_bookings, aroha_booking_profiles, aroha_booking_quotes, aroha_booking_requests, aroha_booking_cursors, aroha_booking_audit, aroha_booking_outbox, aroha_booking_credits and aroha_booking_limits. Existing deny-all rules protect these; only backend Admin SDK accesses them. Bounded audits/outbox exclude comments, names and emails. Email delivery not_configured; no historical replay is enabled. CMS source/public content is untouched.

Completed reservation credits are coalesced across overlapping or adjacent dates for the same owner; splitting one continuous visit cannot inflate tiers. Credit records are immutable in identity and superseded by an active merged interval; profile counts update in the completion transaction. Booking metadata TTL applies only to quotes (after expiry+1day), idempotency receipts(90days) and cursors(15minutes), never reservation/inventory correctness. Contact email is a protected reservation-specific read.
